## 二、核心业务流

### 什么是业务流

业务流是用户操作系统的完整路径。画业务流的目的不是画图本身，而是**在写代码之前想清楚操作路径上的每个环节**。

### 通用操作模式

fasthtml-desktop 应用的所有操作都可以归纳为三种模式：

**模式 A：表单→处理→反馈**

```
用户打开页面 → 填写表单/选择文件 → 点击按钮
  → [HTMX 请求发到 FastHTML 路由]
  → 路由调用后端逻辑（数据处理/文件读写/Agent 推理）
  → 返回 HTML 片段 → 页面局部更新
  → 用户看到结果
```

**模式 B：列表→详情→操作**

```
用户看到数据列表 → 点击某一行
  → [HTMX 请求]
  → 路由查询数据 → 返回详情 HTML
  → 用户执行操作（编辑/删除/导出）
  → [另一个 HTMX 请求] → 返回更新后的列表
```

**模式 C：长时间任务→进度反馈→完成**

```
用户触发一个耗时操作
  → [HTMX 请求] → 路由启动后台线程
  → 前端通过 SSE 接收进度更新
  → 任务完成 → 前端展示结果
```

### 如何设计业务流（示例方法）

> 以下以"文件批量重命名工具"为具体示例讲解业务流设计方法。
> 该示例可替换为你的业务场景——核心是**主路径→异常路径→边界路径**的三步法。
>
> **常见场景映射参考**：
> - 查询/搜索型：输入条件 → 查询API → 展示结果列表 → 点击查看详情 → 导出/下载
> - 数据处理型：上传文件 → 解析校验 → 处理转换 → 预览结果 → 下载导出
> - 监控/看板型：自动刷新 → 数据聚合 → 可视化展示 → 异常告警
> - 配置管理型：列出配置 → 编辑表单 → 校验存储 → 即时生效

第一步：列出所有操作路径

```
路径 1（主路径）：选择文件夹 → 预览重命名 → 执行 → 完成
路径 2（异常）：选择不存在的文件夹 → 提示错误
路径 3（边界）：文件夹没有任何文件 → 提示空文件夹
路径 4（取消）：预览后不满意 → 修改参数重新预览
```

第二步：为每个路径画步骤和状态

```
路径 1：选择文件夹 → 填写前缀 → 预览 → 确认 → 执行成功 → 显示结果
                                                        ↓
                                                  执行失败 → 显示错误

路径 2：填写不存在的路径 → 提交 → 服务端校验 → 返回错误提示
```

第三步：确定每个步骤的技术实现

| 步骤 | 实现方式 |
|------|---------|
| 用户输入文件夹路径 | Form + Input |
| 点击预览 | hx_post |
| 后端生成新文件名列表 | Python pathlib 遍历 |
| 后端返回 HTML 片段 | routes | services |
| 用户确认执行 | 另一个 hx_post |
| 执行重命名 | Python os.rename |
| 进度反馈 | HTMX 同步等待（重命名很快，不需要 SSE） |

### 设计准则

- **先画路径，再写代码**：主路径优先，异常路径其次，边界路径最后
- **一个操作一个路由**：不要在一个路由里做多件事
- **耗时任务必须用 SSE**：超过 3 秒的操作必须通过 SSE 反馈进度，不能阻塞界面
- **失败必须有回显**：每个业务流必须设计失败状态下的用户提示
