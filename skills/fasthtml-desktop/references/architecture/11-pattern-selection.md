## 十一、架构模式选型

### 可选模式

技术栈虽然锁定（FastHTML + pywebview + PyInstaller），但模块组织方式仍有选择空间：

| 模式 | 适用条件 | 优势 | 劣势 |
|------|---------|------|------|
| **Monolith-first**（默认） | 功能单一、< 300 行、单开发者 | 启动快、零抽象开销 | 代码膨胀后难以分离 |
| **Layered（三层）** | 300-1500 行、有数据存取、3-5 页面 | 职责清晰、依赖可控 | 代码量少时显得笨重 |
| **Plugin-based** | 核心框架固定但功能可热插拔 | 扩展性好 | 需要设计插件接口，前期成本高 |
| **Event-driven** | 多 Agent 协作、异步任务链 | 模块解耦彻底 | 桌面单进程场景极少需要 |

### 选择决策树

```
功能 < 300 行？
  ├─ 是 → Monolith-first（单片型）
  └─ 否 → 需要数据存取？
            ├─ 是 → 数据表 > 3 张？
            │         ├─ 是 → Layered（三层：routes/services/models）
            │         └─ 否 → Monolith-first
            └─ 否 → 纯逻辑工具 → Monolith-first
```

### 决策追溯约束

每个架构决策必须能追溯到一条**硬约束**：

```
选择了 Layered 模式（决策）
  └─ 因为 app.py 超过了 400 行且出现了 3 个不相关的功能群组（约束）
      └─ 约束来自：单人维护时超过 400 行的文件阅读成本急剧上升（来源：经验法则）
```

不满足"可追溯约束"的决策需要重新审视。
