## 三、模块分解

### 分解原则

模块分解是把系统按职责切分成内聚单元的过程。规则：

1. **同一类职责放在一起**（路由归路由、逻辑归逻辑）
2. **模块之间依赖方向固定**（上层依赖下层，不反向）
3. **跨模块调用必须通过接口**（函数签名），不能直接操作内部状态

### 三层依赖

fasthtml-desktop 应用统一使用三层结构：

```
路由层（routes/）             ← 感知 FastHTML，处理 HTTP 请求，返回 HTMX 片段
    ↓ 调用
服务层（services/）           ← 不感知 HTTP，纯 Python 业务逻辑
    ↓ 调用
数据层（models/）            ← Fastlite 表定义、数据库操作
```

外加两个独立模块：

```
组件层（components/） → 纯 UI 组件，被路由层引用，不含业务逻辑
工具层（utils/）      → 被任意层引用，纯工具函数，无业务含义
```

### 什么时候拆

以一个文件批量重命名工具为例，演示从单片到拆分的演进：

**阶段 1：app.py 120 行，一个功能**

```python
# 不需要拆分。所有路径逻辑在一个文件中清晰可读。
```

**阶段 2：加上数据统计功能，app.py 350 行**

```python
# 出现两个功能群组：重命名和统计。拆 routes/。
# routes/rename.py + routes/stats.py
# 共享的文件列表逻辑提取到 services/file_service.py
```

**阶段 3：加上数据库记录操作历史，app.py 600 行**

```python
# 数据存取逻辑独立。拆 models/。
# models/history.py 定义操作记录表
# services/ 调用 models/ 读写数据
```

### 拆分的信号

| 信号 | 动作 |
|------|------|
| 一个文件超过 400 行 | 检查是否有多个功能群组 |
| 同一个函数被多个路由引用 | 提取到 services/ |
| 路由函数中有复杂的文件/数据处理逻辑 | 提取到 services/ |
| 组件定义散布在路由之间 | 提取到 components/ |
| 数据库操作逻辑和路由逻辑混在一起 | 提取到 models/ |
| 工具函数出现在路由文件中 | 提取到 utils/ |

### 不拆的信号

| 信号 | 含义 |
|------|------|
| app.py < 300 行，功能单一 | **不要拆。** 单片是最合适的形式 |
| 只有 2-3 个路由 | 拆了反而增加导航成本 |
| 团队只有你自己 | 过度拆分降低开发效率 |
